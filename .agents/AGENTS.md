# Reflective Rust & Research Engineering Agent Doctrine

This document defines the research doctrine, operational guidelines, status honesty rules, authority resolution hierarchy, verification gates, and engineering standards governing AI agents and human collaborators working on **Reflective Rust (RRSA)**, the **Compiler Semantic Graph (CSG)**, and related systems.

---

## 1. System Taxonomy & Canonical Naming

Agents must consistently enforce the official naming stack across all code, documentation, RFCs, and commit messages:

```text
Reflective Rust (Research Program)
  └── Rust Reflective Systems Architecture (RRSA)
      └── Compiler Semantic Graph (CSG)
          ├── Rust Semantic Reflection (Language Subsystem)
          ├── Compile-Time Metaprogramming (Consteval Layer)
          ├── Runtime Semantic Projection (Runtime Subsystem)
          ├── Metaobject Protocols (MOP Layer)
          └── Procedural Reflection Domain (Execution Subsystem)
```

---

## 2. Epistemic Integrity & "Status Honesty" Rules

Agents must adhere strictly to the **Four-Tier Claim Taxonomy**:

$$\text{Documented} \neq \text{Implemented} \neq \text{Tested} \neq \text{Empirically Validated}$$

1. **Never conflate maturity levels**:
   - A feature documented in an RFC is *documented*, not *implemented*.
   - A function with passing unit tests is *tested*, not *empirically validated*.
   - A benchmark written against the implementation it was designed alongside is a fixture, not an empirical proof. State the weaker claim when in doubt.
2. **Permanent Retention of Negative Results**:
   - Abandoned hypotheses, discredited metrics, and disproven architectural directions are recorded permanently in `docs/09-research/rejected-designs.md`.
   - Never prune disproven paths or failed metrics; preserving the record prevents re-proposing abandoned intuitions.
3. **Prospective Pre-Registration**:
   - Experimental evaluations, performance benchmarks, and compiler behavior changes must define pre-registered success criteria and invalidation triggers *before* running tests.

---

## 3. Hierarchy of Authority (`AUTHORITY.md`)

When documentation, code, generated artifacts, or AI outputs conflict, the following canonical resolution order governs:

$$\text{Architecture & Research Doctrine} \to \text{Canonical Ontology & Glossary} \to \text{Language Specification} \to \text{Code / Substrate} \to \text{Generated Artifacts}$$

- **Rule**: Code, generated artifacts, or AI outputs **never** silently alter theory or language specifications.
- **Rule**: If an implementation deviates from the documented architecture, the implementation contains a defect until a formal synthesis determination updates the specification.

---

## 4. Layer Independence & Decoupled Versioning (`VERSIONING.md`)

1. **Independent Version Bumps**:
   - Theory, compiler interfaces, runtime projection adapters, and example crates move on independent version paths.
   - A patch to the specification does not force a release bump in generated crates.
   - Cross-layer compatibility must be declared in an explicit conformance record - never inferred from matching version numbers.
2. **Zero-Dependency Core Substrates**:
   - Core semantic graphs and static reflection handles (`core::meta::Info`) must have zero external dependencies.
   - Runtime projection and host integrations are optional adapters, never required core dependencies.

---

## 5. Verification Gates & Execution Standard

Before proposing a pull request or merge, agents must run the full verification gate:

```bash
# 1. mdBook & link integrity check
node scratch/verify-links.mjs

# 2. Structure & file existence check
python3 scripts/check-structure.py

# 3. Standardize frontmatter & navigation headers
node scratch/standardize-docs.mjs

# 4. Check layer changelog diffs
python3 scripts/check-changelogs.py

# 5. Rebuild agent-first single-file corpus
node scripts/gen-llms.mjs
```

### Verification Rules

- **Gates That Cannot Fail Are Not Gates**: Every check must be proven capable of failing when fed a defect before being trusted in CI.
- **No-Op Protection**: CI workflows must report how many assertions *actually executed*, ensuring skipped or category-error jobs cannot produce a false green check.
- **Git Voice**: Use clean, human engineering prose. No AI attribution trailers (`Co-Authored-By`, `Generated by AI`), no tool session IDs in tracked commits or docs.

## 6. Concentric Scopes & Staging

All work must be categorized into one of the three concentric scopes:

- **Scope I (Near-Term)**: Static Semantic Reflection & Compile-Time Metaprogramming (`docs/00-foundations/`, `docs/03-rust-language-proposal/`, `docs/08-reference/`).
- **Scope II (Mid-Term)**: Compiler Semantic Graph (CSG) & Runtime Semantic Projection (`docs/04-runtime/`, `docs/05-metaobjects/`, `docs/07-compiler/`).
- **Scope III (Long-Term)**: Reflective Environments, AI Tooling & Semantic Spatial Projection (SSP) (`docs/06-procedural-reflection/`, `docs/09-research/`).

## 7. Agent-First Publishing & `llms-full.txt` Context Architecture

To maximize AI agent reasoning efficiency and eliminate context truncation, Reflective Rust maintains an **Agent-First Publishing Architecture**:

### Core Invariants
1. **Single-Pass Deterministic Context (`llms-full.txt`)**:
   - `llms-full.txt` is an auto-generated, single-file concatenation of the entire 108-chapter research corpus (~250 KB).
   - Reading `llms-full.txt` provides AI agents with instant, zero-search access to all specifications, ontology terms, code samples, and architectural boundaries without multi-step file discovery latency.
2. **Structural Index (`llms.txt`)**:
   - `llms.txt` acts as the machine-readable manifest mapping every file under `docs/` to its canonical label and reading order.
3. **Automated Downstream Generation**:
   - `llms.txt` and `llms-full.txt` are **100% programmatically generated** via `node scripts/gen-llms.mjs`.
   - In accordance with [`AUTHORITY.md`](../AUTHORITY.md), generated artifacts are downstream projections and must **never** be manually edited.
